# 检索与证据策略

企业与项目知识共用原件解析、范围过滤、混合召回、重排、相关性筛选、证据组装和引用输出管线。最终证据与候选诊断是不同输出；候选召回成功不能直接证明回答或引用正确。

## 当前管线与指标含义

1. `knowledge_index` 保存原件、解析结构及来源位置，用配置身份判断索引是否兼容。
2. `knowledge_retrieval.inspect` 先限制当前租户、项目、文档版本与就绪状态，再召回候选。
3. 向量与 BM25 经 RRF 融合后重排，随后做相关性、可回答性和证据覆盖检查。
4. 最终 `chunks` 和 `evidence_text` 进入生成；诊断候选不作为额外证据。
5. 回答和引用经应用适配器校验，保留来源及页码、节点等结构位置。

当前查验输出 `pipeline=retrieval`。规则模式不等于校准通过，重排分数不是正确概率。完整解析行为见 [数据管线](data_pipeline.md)，模型与服务准备见 [部署](deployment.md)。

CMRC 的答案位置 Hit@K 只检查前 K 条候选中是否至少一条来自正确原文并包含有效答案字符位置；不是 K 条均正确，也不是完整证据召回、回答正确率或引用正确率。本次 200 题仅有 182 段原文，答案均在库中。实际结果及限制见 [评测报告](evaluation_report.md#cmrc-20261012)。

确定性演示知识保留在 `backend/rag.py`；删除 `knowledge` 目录不移除业务知识功能。

## 查询边界与证据组装策略

本次沿用现有三路召回、Cross Encoder 和相关性分类器，不新增生成模型调用。只作用于 知识检索 查验流程；Chat / Agent 的检索入口没有切换到 知识检索。

### 查询与边界

- 问候以外默认检索；类型识别不承担拒绝检索职责。
- 类型可组合：fact / enumeration / condition / identifier / comparison。未命中规则时回退 fact。
- 普通问题每路最多 30 个候选，重排最多 32 个，最终最多 8 个单元。
- 枚举、比较问题每路最多 60 个候选，重排最多 96 个，最终最多 64 个单元。证据仍受 600 / 1200 / 1800 token 档位限制。
- 条件题追加条件/例外查询；明确的比较对象分别召回，并在重排输入及最终预算中平衡两侧；无法可靠拆分对象时保留原问题。
- 编号题提高精确路线融合权重，避免使用普通英文问句词替代编号查找。

授权文档 ID 和 tenant 同时进入 BM25、向量和精确 SQL。空授权集合不调用模型或索引。OpenSearch 返回 ID 先经 SQL 交集再取得正文。补充查询只允许授权文档；组装前重新读取可见文档，过滤正文及诊断中的失效来源。

### 证据角色及结构修复

原有相关性分类器判定通过的候选作为 direct。未通过的候选只能凭与 direct 的明确关系成为 supporting：同一节点分片、同一记录、显式章节引用。没有 direct 时，supporting 不能独立形成答案。

枚举从已定位的结构范围扩展：同一列表标识、同一表格、同一 JSON 父对象。新发现的同范围条目是独立 direct 事实。表头和 JSON path 沿用索引中的原文上下文，列表标题保留在 heading 中。既不按 previous/next 自动扩展，也不把同一标题下所有段落当作同一个列表。

普通补充最多 12 个单元，枚举最多 64 个，查询多取一个用于识别截断；达到上限输出 repair_limit。没有明确引用关系的主规则/例外，不推断链接，完整性保持 unknown。

### 预算和冲突

- 核心事实与其必要 supporting 一起计费；装不下时整包省略，避免保留主规则却裁掉已识别的例外。
- 原文相同、来源版本和结构范围相同的事实去重，保留重复片段 ID。不同文档、版本、路径、记录不合并。
- 对原文句子做保守的覆盖比较：优先尚未覆盖的事实，相关度用于同等覆盖时排序。只调整选择顺序，不改写原文、不删除否定词，也不声称识别了所有语义同义句。
- 比较题按显式查询分支交替选择证据，降低单侧挤占预算的风险。
- 冲突在预算裁剪前检测：同一明确 JSON path 的不同内容保留为潜在冲突。该检测仍保守，不代表已经实现任意自然语言矛盾识别。

### 兼容输出

保留 `status` 的既有值：evidence_found / budget_limited / source_conflict / insufficient_relevance / index_unavailable。

新增 `pipeline_schema=2`、`query_types`、`result_status`（evidence_found / insufficient）、`budget_limited`、`conflict`、`completeness` 和 `omission_details`。预算受限与冲突可同时为 true。片段携带 evidence_role、supports 和选择原因。证据没有经过全范围完整性证明，因此 completeness/coverage 保持 unknown，不把候选集读完误报为知识库答案完整。

### 发布与验证

解析 schema 从 2 升为 3，以保存 Markdown / DOCX 列表范围。旧 知识检索 索引需通过现有 `POST /api/knowledge/{document_id}/reindex` 重新排队构建；没有修改数据库表结构。

发布配置与评测报告都必须匹配 `pipeline_schema=2`。评测输入行也必须来自当前流程，旧行不会因为重新生成报告而自动通过。旧发布文件保持不动，新流程必须重新跑锁定语料和模型/延迟对比后才能通过门禁。本次没有部署、重建线上索引或伪造校准报告。

回归覆盖：超过 8 项的枚举、无关列表排除、三级证据、主规则与例外原子预算、重复及重叠事实、双侧比较、预算外冲突、空 ACL、BM25 前置过滤、向量 SQL 约束、恶意索引 ID 的 SQL 交集、返回前失效文档过滤和结构扩展上限。测试中的向量距离、tokenizer 和 reranker 使用替身；真实模型质量和 PostgreSQL 执行耗时仍需发布评测。

## 聊天检索范围与回答方式

> 本节保留页面、范围与规则检索说明；真实企业知识检索使用统一 knowledge_retrieval 管线，具体参数以当前配置为准。

### 页面与历史记录

左侧显示当前账号、当前空间的历史对话，可按标题或问答正文搜索。点击后加载原消息、附件与引用，继续提问时保留原项目范围。地址中的 `conversation` 参数支持刷新恢复和浏览器前后导航，不授予其他人访问权限。

新建对话先进入空白页，首次发送或上传才保存记录。新消息记录发送时间，对话按最近消息排序，并在页面分为今天、昨天、最近 7 天与历史对话；早期未记录时间的对话保留在历史分组。侧栏独立滚动、条目固定高度；手机从左上角打开历史抽屉。项目范围在顶部调整，长期记忆在侧栏弹窗中管理。

每条历史对话右侧的「⋯」可重命名、归档或删除。归档保留全部消息、附件与引用，在「已归档」中可以查看、搜索、恢复或删除；归档对话只读，恢复后才能继续提问或修改附件。重命名和归档使用会话版本检查，防止多窗口覆盖。删除需确认，永久移除该对话及其附件，不删除项目资料或长期记忆。

有项目创建权限的账号可从侧栏「创建项目」进入既有实施资料表单；提交成功后返回助手，并选中新项目范围。项目仍为草稿，不自动启动实施 Agent。通过此入口创建的是平台实施项目，不是新的知识可见性分组。

### 范围

项目对话绑定后不变。仅检索本项目需求、实施材料、允许查看的交付物、本项目知识、公司通用知识及本对话附件。平台操作手册可以在各范围使用。明确询问其他项目时返回范围提示，不调用模型代答。切换范围需新建对话。

当前空间对话可检索公司通用知识、当前账号有权查看的项目知识、本对话附件，并查询授权项目状态。它不是单项目范围，也不是整个平台的无限权限。

知识文档以 `project_id` 标记项目归属，空值表示公司通用。范围条件在候选检索与排名之前应用，不能依赖 LLM 自觉保密。同一标题的新版本保持原范围；旧版、停用和未就绪版本不参与检索。历史对话是当时的快照，不代表本轮重新检索；附件删除不会改写历史。

### 实际检索步骤

1. 校验客户身份、空间、会话所有权及项目权限。
2. 使用当前问题检索；指代式追问才附带上一轮问题，不无条件拼接历史话题。
3. 附件和项目材料按标题、段落及约 500 token 分块，重叠约 80 token。中文使用重叠双字词项，英文和项目编号使用词项匹配；候选按命中数排序，最多 4 个本地片段。
4. 公司知识先过滤范围、版本和索引状态，再召回最多 3 个片段。本地 SQLite 使用词项交集；PostgreSQL 可配置全文与向量检索、倒数排名融合和重排。仅配置 LLM 不会自动让 SQLite 变成向量检索。
5. 补充平台手册、问题相关的 OpenAPI 契约及授权实时项目状态。项目是否完成以实时状态为准，计划书和演示 FAQ 不能代表已执行。
6. 有真实 LLM 时，把问题、受限上下文、用户主动保存的记忆和证据交给模型，生成自然语言并校验引用。未配置 LLM 时，只生成规则化状态说明或最多两段短摘录；完整片段在折叠来源中查看，不把 JSON 当成回答正文。

当前词项匹配可能漏掉同义表达，也可能把含相同词语的无关段落排在前面。召回来源不等于已经证明答案；语义召回与真实模型综合回答需要分别配置和评测。范围过滤即使在无模型、模型故障或语义匹配较差时也必须生效。

## 历史查验专用流程设计

> 历史方案参考：inspection_v2 与 RAG_INSPECTION_Agent 是旧设计描述，不能作为当前部署步骤。当前查验返回 pipeline=retrieval，并复用统一检索与证据管线。

新流程只作用于 `POST /api/knowledge/inspect`。默认 `RAG_INSPECTION_Agent=false`，正式聊天、MCP 和 Agent 不切换。

### 服务与部署

先从当前源码构建检索镜像（Dockerfile.retrieval），再更新检索服务和 API。重排接口 `/v1/rerank` 向旧 `index` 结果添加原生 `score`；模型名称与 revision 必须匹配。`/v1/token-counts` 使用 embedding tokenizer 精确计数，不调用生成模型。

设置 `RAG_INSPECTION_CALIBRATION` 可指定校准报告，默认 `evaluations/inspection_calibration.json`。报告必须通过验收且匹配模型、索引标识、窗口配置、流程版本，否则打开功能开关也会返回明确的 503，不降级伪装成精选结果。

运行 `.venv/Scripts/python.exe -m scripts.evaluate_inspection` 对现有 XL-107 夹具进行只读评测，输出详细报告与校准报告。40 题为逐条编写的原文片段标注，尚不代表独立人员完成了人工复核。标注包含相关章节、完整事实原文、否定/例外和干扰章节；对完整语句而非几个关键词检查覆盖。

通过条件：验证集相关块召回率 ≥95%；必要事实覆盖不低于旧 Top-5；事实题 token 节省率中位数 ≥25%；预算违规、范围泄露和验证集无答案误命中均为零。校准与验证题分开，不用验证集回调阈值。失败时报告保留 `passed:false`，功能开关继续关闭；不得手动改成 true。

### 接口

请求新增 `evidence_budget:600|1200|1800`，默认 1200。新流程返回 `pipeline:inspection_v2`，`chunks` 为精选原文证据，`evidence_text` 是按引用、标题、章节、正文序列化的预算边界。BGE token 数包含整个序列化结果，非生成模型 tokenizer token。

`diagnostics` 包含召回、补充、相关和保留数量，原始/最终 token、去重节省 token、预算省略 ID 和带原因的候选。诊断信息仅供查验，不能作为以后生成请求的 evidence。

状态：`not_needed` 无需检索；`not_found` 无候选；`insufficient_relevance` 有候选但不够相关；`found` 返回证据；`budget_limited` 因预算或最多 8 块限制省略相关内容。服务失败使用非 2xx，与无结果区分。

### 已知边界

枚举/章节引用补充是有界启发式，不证明获得了所有事实。只检查已通过重排筛选的文档，每文档最多 8 块、总计最多 16 块、一轮补充；全部重新用原问题评分。既有约 220 token 块和 30 token 重叠不改变，无索引迁移。

文本只做可验证重叠去除和按完整段落/表格行抽取，不改写。不能容纳的独立长段可能整段省略，此时返回预算不足状态。界面格式清理只影响呈现；展开原文可检查精确 evidence 内容。

回滚：将 `RAG_INSPECTION_Agent=false` 并重载 API，保留报告用于追查。模型服务新增字段对旧消费者兼容，不需回滚知识库或向量数据。
