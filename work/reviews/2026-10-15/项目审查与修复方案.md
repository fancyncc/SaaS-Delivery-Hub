# 项目审查与修复方案

审查日期：2026-10-15。对象：当前工作区源码、上一轮尚未提交的 RAG/UI 修改、现有测试及审查时的本地部署配置。

本轮仅审查，未修改业务代码、运行配置或已有账号。状态修改探针均在新建的隔离 SQLite 数据库运行；对已有服务只做配置读取、Redis PING，以及无登录、无有效文件的上传拒绝检查。续查阶段 Docker 已停止，未为审查重新启动，所以本报告不会把本地 Python 包版本等同于当前容器镜像版本。

## 一、结论与证据边界

存在一个可在已观察配置下造成账号接管的紧急问题，以及审批并发、资源保护、授权资料检索与数据清理等具体缺陷。建议先处理认证和网络暴露，再处理审批/文件任务，随后统一知识授权和引用契约。

本次验证：

- 全量收集 552 个测试，548 通过、4 跳过、0 失败，耗时约 30 分钟。跳过的是 Agent、业务流程、注册导入、聊天四项浏览器测试。
- 全仓库 Ruff 通过。
- Mypy 检查 113 个后端文件，5 个文件中存在 20 项类型错误。部分是 Windows 平台声明差异，不能将全部类型错误解释为运行时故障。
- 9 个定向隔离探针复现了以下矩阵中的问题；相关日志和脚本保存于本目录 `evidence/`。
- `pnpm audit` 返回 8 条公告命中：5 高、3 中。这是依赖公告数量，不是已确认可利用的业务漏洞数量。
- 对本地 Python 环境通过 OSV 查询了依赖告警，并核对部分项目维护者公告；未将全部告警判断为当前功能可利用漏洞。

全量单元测试通过与以下缺陷并不矛盾：既有测试没有覆盖邮件调试配置的接管链路、审批上传交错、协作方结构索引授权、引用元数据保留及开启外键后的知识清理等场景。

## 三、逐项问题与具体修复

### F01：密码重置链接在公开响应中泄露

位置：`backend/auth_routes.py:350`、`:372`，`backend/config.py:43`，`docker-compose.yml` 的 API 环境配置。

`MAIL_DEBUG` 默认 true，找回密码接口在调试模式将 `preview_url` 返回给未登录请求。审查时从运行容器读取到 `mail_debug=true`；主 Compose 没有显式传递 MAIL_DEBUG，因此仅在主机 `.env` 写 false 不足以保证容器关闭它。

隔离结果：不知道原密码、无需进入邮箱，取得响应中的链接后重置返回 200，新密码登录也返回 200。已绑定邮箱的账号存在受影响路径。未对已有账号执行该操作。

解决：

1. 对公开 API 移除包含一次性凭证的响应字段；开发验证改用本地邮件收件箱或受控 CLI。
2. MAIL_DEBUG 默认 false；为生产环境增加启动校验，拒绝调试凭证输出和默认引导口令。Compose 明确传入邮件与安全相关配置，部署后读取实际容器设置核验。
3. 配置 SMTP/邮件 outbox 的真实消费者，保证关闭 debug 后找回密码确实可送达。不要仅改开关后让用户永远收不到链接。
4. 修复部署时按账号风险制定旧会话/未用重置令牌失效和凭证轮换方案；本轮没有执行这些状态变更。

验收：已知和未知邮箱的公开响应均不含令牌、URL、是否存在等敏感差异；未持有邮件链接不能重置；邮件链路在非 debug 模式可完成。

### F02：必须改密只是提示字段

位置：`backend/db.py:62`、`backend/auth_routes.py:162`、`backend/security.py:88`、`frontend/src/router.ts`。

bootstrap 管理员设置 `must_change_password=true`，登录返回该字段，但服务端授权没有强制阻断，前端路由也未使用该标记。隔离环境以初始管理员登录后，标记仍为 true，却可读取 `/api/platform/users`，状态 200。

解决：使用限制权限的引导会话；服务端只允许查看必要自身信息、设置新密码及退出。提供验证当前凭证的初次改密入口，完成后撤销引导会话并创建正常会话。前端路由只承担引导，不能替代服务端限制。生产部署拒绝已知默认引导口令。

验收：标记为 true 的账号访问敏感读写接口均被拒绝，直接 HTTP 调用也不能绕过；改密成功后旧会话失效，权限恢复。

### F03：密码重置令牌生命周期不完整

位置：`backend/auth_routes.py:378`—重置处理；`backend/models.py:191`—令牌模型。

找回可签发多条有效令牌；一次成功改密只把当前令牌标记 used，不使同一用户更早的未用令牌失效。隔离测试先签发 A/B，使用 B 改密后，A 仍可再次改密，返回 200。另外，消费使用 SELECT 检查后再写 used_at，没有条件 UPDATE 或行锁，不能证明并发请求只消费一次。

解决：按统一锁顺序锁定用户，条件 UPDATE 消费目标令牌并 RETURNING，随后在同一事务内使该用户其他未用重置令牌失效、更新密码、撤销会话并写审计。签发/重发也应明确旧令牌是否立即撤销。错误响应保持一致。

验收：使用 B 成功后 A 返回 410；同一令牌并发两次只有一次成功；两个不同令牌并发也只能完成一次有效重置；测试必须包含 PostgreSQL。

### F04：基础设施端口暴露

位置：`docker-compose.yml:79`、`:164`、`:169`。

实际检查到 Redis `PING` 无认证返回 PONG，主机映射为 `0.0.0.0:6379` 和 IPv6 全接口。PostgreSQL 映射 `0.0.0.0:5433`。API 也直接映射主机端口，可绕过网页代理。是否可从公网访问还受防火墙和路由影响，本次未做外部探测，不能直接声称已公网暴露或可远程执行代码。

解决：内部服务仅在 Compose 网络通信；必要的开发映射绑定 `127.0.0.1`；Redis 配 ACL/认证并同步 Celery、限流器和进度客户端；数据库使用独立低权限运行角色；正式环境只公开 TLS 入口，限制 API 直连。不能只修改浏览器入口而保留其他端口。

验收：非授权网络无法连接 Redis/数据库/API 内部端口；正确凭证客户端正常，匿名 Redis 被拒绝；服务重启后配置仍生效。

### F05：任务文档与审批快照存在竞态

位置：`backend/knowledge_routes.py:27`、`:37`、`:276`；`backend/project_task_routes.py:178`、`:204`、`:223`。

上传检查任务不是 pending_review/done 时没有锁任务行。审批提交会锁任务并冻结当时 document_ids，但上传能在早先通过检查后、审批提交完成后继续插入关联。隔离探针安排此交错，得到 pending_review、审批冻结 1 份、实际关联 2 份，后来的上传仍成功。

解决：上传与提交审批都按相同顺序锁定任务行，并在锁内检查状态和版本。任务材料变化增加任务版本；提交时校验文档有效、解析完成且可审阅，冻结文档 ID、版本、原件摘要/正文摘要。审批页面显示冻结材料，决定接口验证对应快照。每个审批轮次的材料不可被后续上传覆盖。

验收：确定性并发测试中，提交先获得锁后，迟到上传返回 409；上传先完成时，该文档必须进入本轮快照。两种顺序均不出现审批集与实际集漂移；旧审批轮次不变。

### F06：昂贵检索缺少调用方资源预算

位置：`backend/knowledge_routes.py:72`；对照 `backend/chat_routes.py`、`backend/chat_mcp.py` 已有限流的入口。

查验会调用向量、重排和 tokenizer 服务，但没有用户/租户限流或请求并发预算。探针替换模型后连续 40 次查验全部 200，无 429。该结果证明没有入口配额，不是实际模型承载能力压测。模型队列虽有总容量限制，却不能阻止某个账号占用共享容量。

解决：在昂贵操作之前对用户、租户及全局分别设置速率与并发预算；配置可观测的每日成本/工作量上限；超额返回结构化 429 和 Retry-After。上传/重建索引也纳入配额。Redis 故障时按部署模式明确降级策略，避免生产环境默默变成各进程独立计数。

验收：边界内请求正常，超额不进入模型；两个账号之间有公平性；服务异常不绕过配额；断连释放调用方占位，模型队列状态可观察。

### F07：聊天附件没有复用可终止的解析隔离

位置：`backend/chat_routes.py:231`、`:239`；对照 `backend/knowledge_index.py:136` 与 `backend/document_parse_process.py:14`。

知识文件的 PDF/PPTX/XLSX 解析使用子进程，有父进程超时和 Linux 内存限制；聊天附件直接 `asyncio.to_thread(parse, ...)`，在 API 进程中解析同类不可信二进制。线程不能被 asyncio 超时安全终止，单文件压缩体积限制也不能替代解析 CPU/内存限制。

解决：统一解析服务；聊天附件也经过受限工作进程/队列。限制解压大小、页数、OCR 页数、内存和总时长，解析完成后再发布附件；对 DOCX 等 XML/ZIP 路径统一评估隔离。保留现有原文与警告契约，向前端报告 pending/failed/ready。

验收：超时和异常样本仅结束解析任务，不拖垮 API；有界合法样本正常；重复超时不积累后台线程/进程。未在现有服务投放恶意文件。

### F08：依赖公告命中与可达性

位置：`frontend/package.json:6`—`:8`，`frontend/pnpm-lock.yaml`，`pyproject.toml`。

前端命中 8 条公告，其中 Vite 7.1.9 是多个文件读取/路径检查问题的受影响版本。项目 dev 命令显式 `--host 0.0.0.0`，且本机为 Windows，因此一旦使用该命令向网络开放开发服务，具备相应风险前提。nginx 托管构建产物不等于运行 Vite 开发服务器，不能将两者混为一谈。[Vite 维护者公告](https://github.com/vitejs/vite/security/advisories/GHSA-fx2h-pf6j-xcff)列出 7.3.5 为相应 7.x 修补版本。

本地 Python 的 pypdf 为 6.18.0，命中内存和长时间解析问题，相关路径用于用户文件处理。[字体解析内存公告](https://github.com/py-pdf/pypdf/security/advisories/GHSA-g9cg-prrw-2r8q)、[嵌入文件耗时公告](https://github.com/py-pdf/pypdf/security/advisories/GHSA-v247-6f48-mgcj)分别列出 6.18.1、6.19.0 修复。应升级到覆盖全部已命中公告的兼容安全版本，再重新扫描，而不是仅满足其中一个最低版本。

边界：Vue server-renderer 公告涉及 SSR，当前项目是 createApp 的客户端应用，未确认该利用路径；PyJWT 的 OKP/JWK 告警不等于当前固定 HS256 官方引用校验可被绕过。Mako/NLTK/urllib3 也应按工具链与业务路径区分。当前容器依赖版本在续查阶段未完成二次读取，需部署镜像 SBOM 核验。

解决：补丁升级与 lockfile/constraints 固定；开发服务默认 loopback；CI 对运行镜像和本地工具链分别扫描，保存 SBOM。高风险可达路径阻断发布，未可达告警保留说明与复核日期，不直接宣称“全部可利用”或永久忽略。

### F09：跨公司协作知识的可读与可检索权限不一致

位置：`backend/knowledge_retrieval.py:53`、`:75`、`:77`；`backend/chat.py:158`；数据库策略见迁移 `0028_project_collaboration.py`。

项目文档读取允许已授权协作公司，但结构检索强制 KnowledgeDocument.tenant_id 和 IndexedDocument.tenant_id 为当前用户租户。探针中协作方能读取文档，检索文档集合却为 0。聊天还有 has_knowledge 的当前租户预检查，可能更早跳过检索。

解决：建立统一的授权文档选择器，输出允许的文档 ID 与所属租户；公司通用知识仍仅限当前公司，项目资料按实际项目授权进入。该集合同时约束 SQL、向量、BM25、补充查询和结果返回；同步检查结构索引的 RLS。不能简单删除 tenant 条件扩大为全库搜索。

验收：有效协作成员可检索授权项目文档；未参与协作的公司、已撤销协作、已移除成员均不能读取或检索；通用公司知识不随协作关系扩散。使用 PostgreSQL RLS 实测。

### F10：聊天证据丢失来源定位

位置：`backend/chat.py:163`、`backend/knowledge_citations.py`、`frontend/src/components/RetrievalAnswer.vue:56`。

下游适配器已提供 document_id、version、heading、location、source_chunk_ids，但聊天 evidence 最后重建字典只保留 id/title/text/source/kind，页码和文档 ID 等丢失。探针注入页码 3、版本 2 的合法证据，结果这些字段全无。前端来源跳转又依赖 document_id 与 page，导致检索成功仍不能追溯。

解决：定义统一 Evidence/Citation DTO，所有路径完整保留来源元数据；证据裁剪在统一预算层完成，避免聊天再次按字符截断破坏已组装证据。前端对 MD/TXT/DOCX 也提供文档链接，PDF/幻灯片/表格按其定位展示。

验收：查验、聊天、Agent 对同一证据的文档 ID、版本、定位和原文一致；刷新历史会话仍可核对其当时版本，旧快照明确标注。

### F11：网页代理与应用上传/超时规格不一致

位置：`frontend/nginx.conf:17`；`backend/document_parser.py` 的大小上限；`backend/knowledge_routes.py` 上传入口。

nginx 未设置 client_max_body_size，现场无登录探针小请求返回应用 CSRF 拒绝 403，而 1 MiB+1 字节的请求直接得到 nginx 413。网页宣称支持 10 MiB PDF、5 MiB Office、2 MiB 其他文件，与实际入口不一致。应用直接端口与网页端口行为不同，用户得到的还是 HTML 错误。

解决：按上传接口设置明确代理上限，含 multipart 开销；应用继续按格式检查精确大小，不能只放大代理限制。统一代理读取超时与后端异步工作预算，长解析采用任务状态查询。前端对 413/504/非 JSON 错误提供正确中文说明，并显示格式对应上限。

验收：经 8080 网页入口分别测试每种格式的上限内、上限外文件，行为与 API 一致；不通过应用直连端口替代端到端验证。

### F12：项目清理链路不完整

位置：`backend/cleanup.py:19`、`:36`，`backend/admin_routes.py:533`，`backend/knowledge_index_models.py:14`，`backend/models.py:533`。

后台清理和管理接口各自实现删除逻辑。动态按 project_id/run_id 删除不足以处理 IndexedDocument.origin_id 指向 KnowledgeDocument 的关系；管理接口更只清理部分旧表。开启外键的隔离库中，过期项目带知识原件时清理抛 IntegrityError。默认 SQLite 测试没有启用同等外键约束，可能掩盖此类问题。

解决：合并为单个维护服务，明确依赖顺序：结构单元/节点、索引原件、任务关联、知识原文、业务与历史数据，最后项目。保留审计与快照的合法保留约束。对 OpenSearch、S3 等派生数据用可重试清理 outbox，不能假定 SQL 删除会自动清除外部存储。数据库约束和级联策略需迁移明确，不用关闭外键解决。

验收：SQLite 外键开启与 PostgreSQL 下均可清理含知识、任务、会话、Run 快照和交付物的完整过期项目；未满保留期拒绝；失败可恢复，不残留其他租户数据或破坏审计。

### F13：解析预算超过任务执行上限

位置：`backend/worker.py:45`、`:240`，`backend/knowledge_index.py:344`，`backend/document_parse_process.py:14`。

Celery 全局 soft/hard 为 240/300 秒，PDF 子进程允许 600 秒，索引单文档允许 630 秒；一个索引任务还会在同租户事务中处理多个来源。合法但慢的扫描件可能先被外层任务终止，单文档错误/进度的事务也可能无法提交。此项为代码与配置冲突确认，没有以长时恶意样本验证生产故障。

解决：按文档或有界批次拆任务，独立提交阶段/结果，避免长期持有事务跨越解析和网络调用。明确排队、解析、嵌入、发布、任务外层各层预算，外层应大于内部总预算和收尾时间；增加 worker 丢失后的租约回收、指数退避、错误分类和可见重试状态。不能只无限提高 hard limit。

验收：慢合法 PDF 能完成或明确失败；worker 被杀后任务最终可恢复/终止，不永久显示等待；一份故障文档不会回滚同批所有完成文档。

### F14：质量门禁没有覆盖关键运行条件

位置：`.github/workflows/ci.yml:22`—`:23`、`tests/conftest.py`、`pyproject.toml`。

后端 CI 跑 Ruff 与 pytest，没有 Mypy 门禁；当前检查有 20 项类型错误。常规测试默认 SQLite，CI 主流程没有真实 PostgreSQL/RLS 服务矩阵。独立 browser job 确实存在，不能说项目没有浏览器测试；本轮全量 pytest 中那 4 项没有启用。

解决：先修清类型基线，区分类型声明问题与实际缺陷，再加入 Mypy。增加最小 PostgreSQL 权限、事务/竞态、外键、RLS 测试；保留代理端口端到端测试；将本次 9 个探针对应场景转为长期回归测试。依赖审计和危险配置检查纳入发布门禁。

验收：类型检查零错误；引入 F01/F05/F09/F10/F11/F12 任一回归时 CI 必须失败；报告明确区分运行、跳过、模拟模型和真实服务验证。
